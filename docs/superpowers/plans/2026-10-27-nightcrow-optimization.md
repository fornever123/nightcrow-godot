# 夜鸦游戏完整优化计划

日期：2026-10-27  
范围：`E:/00game/nightcrow-godot` 试玩版  
方式：代码、场景、资源、文档、测试和实机画面审计；本轮只形成计划，不改动玩法代码。

## 先给结论

当前项目已经具备可玩的战斗原型，基础稳定性也不错：本轮抽查的 10 组 Godot 测试共 396 项，0 失败；编辑器无解析错误；战斗编辑器构建通过；动画时序和 GitHub 同步测试分别为 21/0、23/0。

下一阶段不应直接继续堆敌人、关卡或特效。项目的主要风险集中在四件事：

1. 当前工作树包含大招重做、音频替换和大量文档删除/改写，尚未形成可回退的基线。
2. “失衡/眩晕连段”和当前实际的“连续击退→挑飞→浮空→终结”存在设计与文档冲突，会导致调参、教程、测试和玩家预期不一致。
3. L2-L4 的长期玩法内核仍未定，继续扩内容会把错误方向固化。
4. 大招、全屏特效、资源仓库和运行时扫描都有明显的质量或性能风险，但需要按阶段验证，不能一次性重写。

建议目标是：先冻结可复现基线，再统一战斗规则和产品循环，随后完成大招可读性与视觉收口，最后做性能、资源管线和发布验收。

## 审计证据与边界

### 已确认

- 主场景是 `scenes/night_trial.tscn`，训练场为 `scenes/training.tscn`；世界和大部分对象由运行时代码创建。
- 主要复杂度集中在 `scripts/gameplay/player.gd`（约 2400 行）、`scripts/night/shade.gd`（约 1500 行）、`scripts/presentation/impact_fx.gd`（约 1200 行）。
- `scripts/night/night_trial.gd` 中仍有硬编码波次、竞技场尺寸和大招伤害参数；`scripts/core/configuration.gd` 读取 `assets/data/battle.json`。
- `night_trial.gd` 和 `shade.gd` 高频调用 `get_tree().get_nodes_in_group()`；`pixel_fx.gd` 每帧 `filter()` 并执行多层特效；背景和全屏 shader 也属于高负载候选。
- `night_trial.gd:770-773` 使用全局 `Engine.time_scale` 做清场慢镜头；玩家自身 hitstop 采用独立计帧，两套时间控制需要统一边界。
- `character_view.gd:38` 在每帧流程调用 `Art.warm()`，需要确认是否完全由缓存吸收。
- `fx_glow_sprite.gdshader` 在 headless 测试中出现 custom sampler 编译诊断，当前测试仍通过，但必须用真实 OpenGL 窗口确认视觉结果。
- 仓库当前跟踪约 7346 个 PNG、3749 个 `.import`、106 个 `.uid`，资源和导入元数据的边界需要明确。
- `docs/玩法内核候选方案.md` 明确写着“内核未定”；`docs/试玩说明.md` 仍按失衡条/眩晕介绍玩法；`docs/HANDOFF-试玩版.md` 又说明 2026-10-21 起已停用失衡/眩晕。

### 当前验证限制

- 全部自动测试循环曾出现不退出的情况，因此没有把“全套测试通过”作为结论。
- `tests/test_editor.mjs` 需要 modifier 服务和活跃 Godot 窗口，本轮没有执行。
- headless 测试不能替代真实 GL 画面验收；大招和 shader 必须增加窗口截图/录屏验收。
- 当前 Git 工作树已有未提交改动。本计划不会替用户清理、回滚、暂存或提交这些改动。

## 优先级总表

### P0：开始任何实现前必须完成

**P0-1 基线与工作树冻结**  
在当前分支上记录提交号、工作树状态、测试基线和大招 WIP 文件清单；创建专门的优化分支或等价快照。先确定哪些未提交文件属于“绝影”大招版本，哪些是误删或历史资料。未经确认不得执行批量清理。

**P0-2 战斗规则单一真相**  
在“保留连续击退主线”和“恢复失衡/眩晕阶段”之间做一次产品决策。推荐先保留当前已经可玩的连续击退主线，把旧 poise/stun 代码标成兼容/实验路径并移出玩家说明；如果要恢复眩晕，则先写状态转移和验收规则，再改代码和测试。

**P0-3 L2-L4 产品循环决策**  
明确一局时长、胜负条件、波次/房间结构、奖励或成长、重开方式，以及是否进入局外成长或本地 PVP。没有这个决策，不新增敌人、Boss、更多场景和长期经济系统。

### P1：确定方向后立即执行

**P1-1 大招“绝影”收口**  
现有 `docs/大招-实机段改进计划.md` 和 `docs/ult-step0-ingame.png` 已经是 WIP，应作为独立工作流完成：解决高清切入与像素战斗场景的风格断层、静止段空、伤害数字和斩击顺序难读、回场过软等问题。每个阶段都要保留帧截图验收。

**P1-2 shader 与战斗反馈修复**  
处理 `fx_glow_sprite.gdshader` 的 custom sampler 诊断；检查角色描边、命中闪白、暗角、慢镜头和伤害数字在真实 GL 窗口中的层级与可读性。headless 通过只能作为逻辑证据。

**P1-3 配置文件校验**  
让 `battle.json` 具备版本字段、必填字段检查、类型检查、动作引用检查、错误路径和可读日志。禁止解析失败时静默返回空配置并继续运行；为旧字段提供一次性迁移或明确失败信息。

**P1-4 资源仓库策略**  
区分原始素材、运行时素材、导入缓存和生成产物；确认 `.import/.uid` 是否纳入版本控制；制定 PNG/WebP、图集、尺寸、命名和压缩规则。迁移必须在干净 clone、编辑器重导入、主场景运行和打包测试后再合并。

### P2：用证据驱动的质量和维护工作

**P2-1 性能剖析与低风险优化**  
先采集 60 FPS 下的 CPU、渲染、内存和峰值帧时间，再决定是否引入战斗注册表、可复用数组、特效池、背景质量档位或 shader 降级。不要凭代码长度直接重写。

**P2-2 数据驱动波次和竞技场**  
把 `night_trial.gd` 的 `ROUND`、竞技场尺寸、敌人上限、重生点和难度倍率迁移到独立 JSON/Resource，并保留编辑器校验。代码只负责执行，关卡数据负责配置。

**P2-3 大脚本渐进拆分**  
在测试锁定行为之后，优先把 player/shade 的输入、状态、命中、移动和展示拆成窄模块；`impact_fx.gd` 只拆公共接口和效果组。每次只拆一个边界，禁止一次性重写战斗系统。

**P2-4 工具链和发布验收**  
补齐 modifier/editor 测试、OpenGL 实机 smoke、干净 clone、Windows 导出、音频和资源缺失检查。把当前“能运行”提升为“可交付、可恢复、可复现”。

### P3：核心稳定后再做

- 暂停、设置、重映射、手柄、文字大小和色盲友好选项。
- 依照 L2-L4 决策扩展敌人、Boss、场景、剧情和成长。
- 统一项目名称“夜鸦 / 月下堤岸 / Night Crow”的产品标题、窗口标题、README 和截图命名。

## 分阶段执行计划

## 阶段 0：建立可回退基线

**目标**：不改变游戏行为，先让后续每一步都能定位回归。

**任务**

1. 保存当前 HEAD、工作树状态、Godot 版本、导出模板状态和测试命令。
2. 给当前未提交文件分组：大招、音频、shader、文档迁移、删除项、工具脚本。
3. 创建优化分支或等价快照；记录当前 396 项 targeted checks 的结果。
4. 记录 headless shader 诊断，并准备一份真实窗口截图基线。

**涉及位置**：Git 工作树、`docs/大招-实机段改进计划.md`、`tests/`、`project.godot`。  
**验收**：任何人可以从快照启动主场景和训练场；能复现测试命令；不需要恢复被删除文档才能运行。

## 阶段 1：统一规则、文档和配置

**目标**：代码、HUD、教程、测试和文档描述同一套战斗。

**任务**

1. 做一次“连续击退 vs 失衡/眩晕”的决策记录，列出保留/删除/实验状态。
2. 更新 `scripts/night/shade.gd` 的注释、状态入口和无效 poise 路径；若保留兼容代码，说明触发条件。
3. 更新 `docs/HANDOFF-试玩版.md`、`docs/试玩说明.md`、README 和情境提示，移除已经失效的失衡条说明。
4. 为 `battle.json` 增加 `schema_version`，补充加载期校验和错误上下文。
5. 对 `ROUND` 和大招数值建立配置来源说明，避免代码常量、JSON、文档三处漂移。

**验收**

- 新玩家说明不会同时出现两套冲突规则。
- 缺字段、类型错误和动作 ID 错误会在启动日志中指出文件和字段，并停止进入不可预测状态。
- 现有战斗测试仍保持通过；如果规则改变，测试名称和断言同步更新。

## 阶段 2：确定并验证核心循环

**目标**：在增加内容前，确认试玩版“为什么好玩、何时结束、为什么重开”。

**建议的最小验证局**

- 一局 8–12 分钟，三处封印/三段战斗结构保留。
- 每段包含普通敌人、一个需要不同处理的敌人、一个明确的清场反馈。
- 玩家拥有清晰的失败、重开、恢复和大招资源节奏。
- 结算至少记录通关时间、最高连击、受击、关键战斗行为和评价原因。

**任务**

1. 设计 5 人试玩脚本：首次游玩、熟悉操作、主动追求高评价、故意受击、重复重开。
2. 记录每个动作的“意图是否被看懂、反馈是否及时、失败是否可归因”。
3. 只调参与提示，不新增大系统；输出一页平衡表：敌人 HP、攻击前摇、玩家资源、波次密度、结算阈值。
4. 依试玩结果决定是否保留当前三段封印结构，还是转向房间/局外成长路线。

**验收**：至少 4/5 试玩者能在不看开发者口述的情况下完成基础连段，并能解释自己为什么受伤或为什么没有触发大招；失败后能在 10 秒内重开。

## 阶段 3：完成“绝影”大招

**目标**：让大招成为战斗高光，同时不遮挡信息、不破坏回场节奏。

**任务**

1. 固定镜头节拍：起手切入、三刀/斩线、敌人延迟裂开、回到战斗；每段规定时长和允许输入。
2. 统一视觉语言：确定高清 cut-in 与像素场景之间使用的暗化、描边、颗粒、色差和缩放策略。
3. 重做静止段的视觉信息：刀线、角色姿态、敌人轮廓、粒子方向必须能在 720p 截图中读出。
4. 重新排布连续伤害数字，确保不会互相覆盖；记录每个目标的受击顺序。
5. 将 `Engine.time_scale` 慢镜头纳入统一时间效果服务，确保重复触发、退出场景和测试失败时都能恢复 1.0。
6. 修复或替换 glow shader，并在真实 GL 窗口逐帧截图。

**验收**

- 720p、默认缩放下，玩家能看清起手、斩线、目标顺序和回场。
- 大招期间不会丢失玩家/敌人状态；取消、死亡、重载后时间倍率和输入状态都恢复。
- 预定关键帧截图通过审查；音频事件与视觉节拍误差不超过 1–2 帧。

## 阶段 4：可读性与视觉整合

**任务**

1. 检查角色与背景的明度、色相和轮廓对比，优先保证敌人预警和玩家位置。
2. 统一命中闪白、重击、弹刀、墙撞、连锁、清场和封印横幅的层级。
3. 把情境提示改成短、可跳过、只出现一次的操作卡；避免旧玩法词汇。
4. 给大招、普通攻击、弹刀和受击做声音响度基线，避免满屏效果时关键音效被盖住。

**验收**：缩小窗口、低亮度显示器和无声音三种情况下，关键危险、命中和大招状态仍可识别。

## 阶段 5：性能与运行时结构

**先测再改**。使用同一波次、同一输入序列和同一分辨率采样。

**优先检查**

1. `night_trial.gd` / `shade.gd` 的 group 全量扫描，必要时建立 `CombatRegistry`，只在对象进出场时更新集合。
2. `encounter.gd:93` 的每帧 `alive.filter()`，改为失效对象回收或按事件清理。
3. `pixel_fx.gd:193` 的每帧数组分配，改为复用缓冲区或倒序删除。
4. `night_backdrop.gd`、`night_light.gdshader`、`char_light.gdshader`、`night_post.gdshader` 的全屏采样和质量档位。
5. `character_view.gd:38` 的每帧 `Art.warm()`，确认后移到初始化、换装或资源缺失时。

**验收**

- 目标设备和默认分辨率下，战斗高峰持续 60 FPS；最低帧、1% low、峰值帧时间有记录。
- 优化前后输入序列的命中、伤害、击退、死亡和结算结果一致。
- 降低特效档位只影响画面成本，不改变战斗判定。

## 阶段 6：资源与仓库整理

**任务**

1. 盘点 7346 PNG、3749 `.import`、106 `.uid` 的来源和使用关系。
2. 规定 `assets/source`、`assets/runtime`、`assets/generated`、导入缓存的边界；保留能重新生成的脚本和清单。
3. 对重复帧、超大图片、未引用音频和旧文档做报告，先报告后删除。
4. 选择少量高频序列做图集/压缩试验，比较加载时间、内存和画面质量。
5. 在干净 clone 执行导入、启动、测试和导出，确认没有依赖本机缓存。

**验收**：仓库体积、首次导入时间、运行内存和画面质量都有迁移前后数据；任何删除都能从源素材或生成脚本恢复。

## 阶段 7：发布和回归门禁

**自动检查**

- Godot headless：动作、战斗、训练、移动、格挡蓄力、空中攻击、大招、地形、音频。
- 编辑器：`--headless --editor --quit` 无解析错误。
- 工具：`test_animation_timing.mjs`、`test_github_sync.mjs`、战斗编辑器构建。
- 配置：JSON schema、资源引用、缺失贴图/音频、导入元数据。

**实机检查**

- OpenGL 窗口：主场景、训练场、连续三波、死亡重开、大招、退出场景。
- 720p 默认窗口与缩小窗口截图。
- modifier/editor 流程（需启动服务时再执行 `test_editor.mjs`）。
- 干净 clone 和 Windows 导出包。

**发布门槛**

- 无阻塞级错误日志。
- 关键战斗和大招截图通过审查。
- 目标硬件达到性能目标。
- 用户文档、控制说明、版本号和已知问题与实际行为一致。

## 建议的任务拆分

### 立即创建的任务

1. `baseline-freeze`：记录快照、WIP 清单、测试基线。
2. `combat-rules-source-of-truth`：统一连续击退/失衡眩晕规则和文档。
3. `battle-json-validation`：schema、错误诊断、迁移。
4. `ult-absolute-polish`：大招分镜、shader、声音、截图验收。
5. `runtime-profile`：固定输入序列和性能采样报告。
6. `asset-pipeline-report`：资源分类、体积、重复和干净 clone 报告。

### 任务依赖

## 暂时明确不做的事

- 不在核心循环未定前增加新敌人、Boss、长期成长或本地 PVP。
- 不直接删除当前工作树中的文档、音频、shader 或美术资产。
- 不用一次性重写替代渐进拆分；不以代码行数本身作为重构理由。
- 不把 headless 测试通过当成 shader、镜头和音频已经通过。
- 不自动生成新的 AI 美术；新素材按现有交接约定由用户提供或明确指定来源。
- 不执行全量机器人长跑，除非本次改动影响整局流程；优先固定场景和短回归序列。

## 需要产品确认的四个问题

1. 最终战斗核心是否正式采用当前“连续击退→挑飞→浮空→终结”，还是恢复“失衡→眩晕”？
2. 试玩版的目标是一局 8–12 分钟的线性战斗，还是房间/局外成长原型？
3. 最终对外名称采用“夜鸦”“月下堤岸”还是 Night Crow？
4. 大招高清切入素材由用户提供，还是继续使用程序化/现有素材完成第一版？

这些问题不影响阶段 0 的基线工作，但会影响阶段 1、2 和后续内容量，必须在扩内容前锁定。

## 本轮审计结论

项目当前不是“不能玩”，而是已经进入需要收口和定方向的阶段。最划算的顺序是：先冻结现状，消除规则与文档冲突，验证一局核心体验，再把大招和视觉反馈做完，最后用剖析数据处理性能、资源和结构问题。这样可以最大限度保留现有可玩成果，同时避免在未定的玩法方向上继续堆代码和素材。
